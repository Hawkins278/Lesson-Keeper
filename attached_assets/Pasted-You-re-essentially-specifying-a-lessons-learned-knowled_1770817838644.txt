3. Scoring logic for “could be better”
For LessonSubcategory scores (only “CouldHaveGoneBetter” lessons affect scoring):

When a subcategory is first seen (first lesson imported or created):

Set FirstRecordedDate = today.

Set CurrentScore = 1000.

Set LastScoreUpdatedAt = today.

Daily decay:

EffectiveScore = CurrentScore - daysSinceLastUpdate.

You can either:

Recalculate lazily on read (compute and display EffectiveScore, and update CurrentScore/LastScoreUpdatedAt then), or

Run a daily job that decrements CurrentScore by 1 for all subcategories where CurrentScore > 0.

When a new CouldHaveGoneBetter lesson is added to a subcategory:

Apply decay since LastScoreUpdatedAt (as above).

Then increase CurrentScore by 200.

Update LastScoreUpdatedAt = today.

Initial “could be better” view:

Group by Subcategory (with Category label).

For each subcategory group:

Show subcategory name, category, EffectiveScore, and number of lessons.

Under each, list lessons by Name (clickable for drill‑down).

Order groups by EffectiveScore descending (highest at the top).

Filters:

ProjectType (multi-select).

When filters are applied, only consider lessons that match, but keep scoring per subcategory global (or offer a “score within filtered set” toggle if you want to get fancy).

This faceted approach maps directly to typical “lessons register” structures used in project templates.​

6. Auth and SSO integration
Given you want “simple login credentials and SSO integration API”:

Implement local accounts (email + password) plus one SSO provider (e.g. Azure AD, Entra ID, Okta, or an open-source IdP).

Use a modern federation protocol such as OpenID Connect or SAML for SSO.

Pattern:

Identity Provider (IdP): central auth (e.g. Azure AD).

App: OIDC client:

Redirects to IdP for sign‑in.

Receives ID token + access token.

Extracts user email/name, maps to local User row (auto‑provision on first login).

Pair SSO with MFA at the IdP for better security.​

Keep attribute mapping documented (email, displayName, unique subject id), as this simplifies troubleshooting.

Provide:

“Sign in with corporate account” (SSO button).

“Sign in with email/password” for simple login (optionally restricted to admins or for break‑glass access).

7. Recommended tech stack (example)
Given your prior interest in Blazor/atomic design, a feasible stack:

Frontend: Blazor Server or WASM, atomic component library for buttons, filters, cards.

Backend: ASP.NET Core Web API with EF Core for data model.

Auth: ASP.NET Core Identity + OpenID Connect integration with your IdP.

Jobs: Background hosted service or scheduled task for daily score decay if you don’t do it lazily.

Storage: SQL Server / PostgreSQL
